# Безопасность и границы текущей беты

## Реализовано

- Одноразовые приглашения: 32 случайных байта, в БД только SHA-256, срок 1–30 дней. Создание пользователя и погашение приглашения — одна `BEGIN IMMEDIATE` транзакция; конкурентный сценарий проверен.
- Пароли: scrypt N=131072, r=8, p=1, соль 16 байт, результат 64 байта. Одновременно не более двух дорогостоящих операций хеширования. Пароли 12–128 символов.
- Сессии: случайный токен 32 байта, в БД только его SHA-256, 7 дней, максимум 20 сессий пользователя. HttpOnly, SameSite=Strict, Secure и `__Host-` в HTTPS. Токенов в localStorage нет.
- CSRF: точное сравнение Origin с APP_ORIGIN + отдельный CSRF-токен, сравнение без зависимости времени от содержимого. Проверяется на всех изменяющих запросах. До входа используется HttpOnly pre-cookie; токен возвращается своим `/api/auth/me`.
- Публичная регистрация не создаёт администратора. Первый администратор — только серверная команда с невидимым вводом пароля.
- Каждая операция с диалогом/изображением проверяет владельца. Файлы не находятся в публичном каталоге. Идентификатор файла не заменяет авторизацию.
- Изображения декодируются sharp, проверяются по формату и числу пикселей, перекодируются без исходных метаданных; SVG не принимается. Имена файлов генерируются сервером. Аватар до 2 МБ, 256×256 WebP.
- SQL с параметрами; SQLite foreign keys, транзакции; ограничения JSON-body 64 КиБ. Встроенный HTML в Markdown отключён, внешние изображения не подгружаются, опасные URL отфильтровывает react-markdown.
- Helmet/CSP, no-referrer, X-Content-Type-Options; приватные ответы no-store. Секреты и тела запросов не журналируются. Ошибки внешнего API возвращаются в обезличенном виде.
- Ограничение частоты запросов в SQLite: общий лимит 240/мин/IP, отдельные лимиты на вход, регистрацию, восстановление, генерации, аватары и приглашения. IP из proxy-заголовков не доверяются по умолчанию.
- Суточные квоты пользователя и сервиса списываются атомарно до обращения к API. Неудачные попытки тоже учитываются, поскольку провайдер мог уже выполнить платную работу. Повторные автоматические запросы SDK отключены.
- На пользователя допускается одна текстовая и одна image-генерация одновременно; тайм-ауты и отмена. Максимальный текстовый ответ ограничен max_completion_tokens, контекст — числом символов и последних сообщений.
- Восстановление: токен 32 байта, SHA-256 в БД, срок 30 минут, одноразовый, ссылка с fragment вместо query. Смена пароля отзывает другие сессии и reset-ссылки.
- При удалении аккаунта каскадно удаляются чаты, сообщения, изображения, сессии и reset-токены; персональная статистика и связанные audit-записи удаляются. Очередь file_gc повторяет неудавшееся удаление файлов.

## Что эта проверка не доказывает

Это прикладная бета, не независимый аудит и не сертификация безопасности. Нет полноценной защиты от распределённого DDoS, двухфакторной аутентификации или проверки владения email. Приглашения ограничивают регистрацию, но не заменяют такую проверку.

Квоты ограничивают число запросов и верхнюю границу output-токенов, но **не являются точным денежным бюджетом**. У разных моделей разная стоимость; лимит бюджета проекта у провайдера настраивается отдельно. Отмена локального запроса не гарантирует отмену уже понесённых расходов.

Необходимо HTTPS-окружение перед публикацией. `TRUST_PROXY=true` допустим только за доверенным reverse proxy, который перезаписывает forwarded-заголовки; приложение должно быть недоступно напрямую снаружи. Безопасный default — false.

SQLite предназначен для одного процесса приложения. Несколько экземпляров одной БД не поддерживаются: восстановление прерванных задач выполняется на старте процесса. Статистика общих расходов сохраняется после удаления аккаунта без идентификатора пользователя.

Файлы и БД не зашифрованы приложением на диске. Для размещения нужны защищённые диски/резервные копии и закрытые права операционной системы. Удаление из резервных копий регулируется сроком их хранения. Тексты, переданные провайдеру, не могут быть удалены локальной командой из его собственных систем.

Редкие аварии между записью файла и транзакцией БД могут оставить несвязанный файл; при эксплуатации следует сверять хранилище с `users.avatar_key`, `image_jobs.file_key` и `file_gc`. Очередь удалений обеспечивает повтор штатных ошибок, но не заменяет резервное копирование и мониторинг диска.
