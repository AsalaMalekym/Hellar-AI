## Поток данных

Браузер обращается только к своему `/api`. Cookie передаётся автоматически, CSRF — в заголовке. Backend проверяет сессию, роль/владельца, валидирует Zod-схему и квоты. Только после этого сервер вызывает OpenAI. Ключ никогда не возвращается клиенту.

При текстовой генерации сначала сохраняются пользовательский запрос и пустой assistant message со статусом streaming. Фрагменты поступают по SSE, содержимое периодически сохраняется, в конце записывается complete/error/interrupted. Повторная генерация заменяет последний assistant message, не дублируя запрос пользователя. Старые варианты ответа не хранятся.

Image-запрос создаёт pending job. После ответа декодируется/проверяется PNG, сохраняется случайное приватное имя, затем обновляется запись. Клиент видит только авторизованный URL по ID job. Переход на другую страницу не отменяет уже запущенную image-генерацию; её результат можно найти в истории.

## Схема данных

- users → sessions, password_resets, chats, image_jobs: каскадное удаление.
- chats → messages: каскадное удаление, порядок по времени и rowid.
- invitations: created_by/used_by обнуляются при удалении пользователя; used_at остаётся, поэтому приглашение не становится пригодным повторно.
- usage: суточный агрегат попыток пользователя и общий агрегат сервиса, атомарное резервирование.
- rate_limits: хеши ключей ограничителей с временем истечения.
- generation_locks: один активный вид генерации на пользователя.
- file_gc: очередь отложенного удаления файлов.
- audit: минимальные события администрирования, без паролей, токенов, промптов и API-ключей.

SQLite включён с WAL, foreign_keys и busy_timeout. Миграции выполняются автоматически на старте и отдельно командой. Recovery отмечает незавершённые сообщения/jobs как interrupted и снимает блокировки только при запуске приложения, а не при каждом открытии БД.

## Переход на PostgreSQL и S3

FileStorage задаёт `put/read/delete`; S3-адаптер должен сохранять приватность bucket и проверку владельца в API. Не следует заменять приватные маршруты публичными ссылками. Для больших файлов стоит перейти от Buffer к streaming API.

Store изолирует соединение и транзакции, но текущие SQL-вызовы синхронны и часть выражений SQLite-специфична. PostgreSQL **не подключается одним изменением DATABASE_URL**. Для перехода нужны async-репозитории, PostgreSQL-миграции, замена `INSERT OR IGNORE`, `instr`, `rowid`, PRAGMA и миграция данных; далее повторяются конкурентные и ownership-тесты. HTTP-контракты, интерфейс, модели доступа и FileStorage менять не требуется.

Для нескольких процессов также нужны распределённый rate limiter, очередь задач, уведомления отмены и централизованное хранение блокировок. Текущая версия рассчитана на один процесс, один локальный persistent volume.
